**선언적인 코드(Declarative Code)**는 프론트 개발 시 자주 만나게 되는 개념이다

### 선언적인 코드
---
토스 프론트엔드 챕터에서는 선언적인 코드를 `"추상화 레벨이 높아진 코드"`라고 여긴다
예를 들어 아래와 같이 주어진 배열의 합을 구하는 `함수 sum`이 있다고 하자

```
sum([1, 2, 3])
```

`sum 함수`는 아래와 같이 for문으로 구현 가능하다

```js
function sum(nums: number[]) {
	let result = 0;
	for (const num of nums) {
		result += num;
	}
	return result;
}
```

여기서 sum 함수는 초기값이 0이며 배열이 갖고 있는 각각의 원소를 순회하여 결과에 더하는 작업을 추상화한다

-  초기값을 0을 가진다
- 각각의 원소를 순회한다
	- 원소의 합을 더한다
- 원소의 합 결과를 반환한다
> 이를 sum이라고 추상화한다

==이렇게 동작에 집중하여 추상화된 sum 함수를 선언적인 코드라고 한다==


- **`for ... of` 문 살펴보기**

```js
	for (const num of nums) {
		 /* 동작 ... */ 
	}
```

위 제어 흐름도 선언적인 코드로 볼 수 있다
배열이 갖고 있는 각각의 요소를 순회하는 동작을 추상화하고 있기 때문이다

ECMAScript 표준에 따라 `for ... of` 가 추상화하는 로직을 그대로 드러내면 아래와 같다

```js
const iterator = nums[Symbol.iterator]();

let step;

while(!(step = iterator.next()).done) {
	const num = step;
	/* 동작 ... */ 
}
```

위처럼 `for ... of` 문은 Iterator를 생성하고, 끝날 때까지 다음 요소를 차례차례 가져오는 작업을 **"각각의 요소를 순회하는 작업"**으로 추상화한다
이런 관점에서 `for ... of`는 선언적인 코드이다



### 좋은 선언적인 코드 작성하기
---
선언적인 코드를 추상화 레벨이 높아진 코드로 보았다
그런데 선언적인 코드는 항상 좋은 것일까?

토스에선 추상화가 항상 좋은 것은 아닌 것처럼 선언적인 코드도 잘 쓰는 것이 중요하다고 생각한다

토스에서 좋은 코드를 판단하는 제 1원칙은 "수정하기 쉬운 코드"이다
비즈니스 요구사항은 항상 빠르게 변하기 때문에 개발자가 기민하게 대응하는 것이 중요하기 때문이다

그러면 선언적인 코드가 언제 수정하기 쉽고, 언제 그렇지 않은지 살펴보자

```tsx
	<SignUpForm 
		onSubmit={
			result => { /* 회원가입 결과에 따라서 특정 동작 수행 ... */ }} />
```

위 컴포넌트는 회원가입 로직을 하나의 커포넌트로 추상화했기 때문에 선언적인 컴포넌트로 볼 수 있다

> **이 코드는 수정하기 쉬울까?**
	먼저 *회원가입 폼을 여러 곳에서 사용한다면*, 각각의 폼을 중복해서 개발할 필요 없이 한 번만 개발하면 되기 때문에 효율적일 것이다

또한 회원가입폼에 변경이 생긴다고 하더라고, 한 곳에서만 바꾸면 다른 화면들 모두 반영되기에 빠른 수정이 가능할 것이다

> **수정이 어려운 지점은 어디일까?**
> 	화면마다 `SignUpForm` 이 조금씩 다르다면, 공통화된 것이 오히려 코드의 복잡함을 가져올 수 있다
> 	- 특정 페이지만 스타일이 조금 다를 경우
> 	- 특정 페이지만 로직 순서가 다를 경우(A 페이지 먼저 띄우기)



### 토스의 선언적 라이브러리
---
- #### useOverlay
  
![[Pasted image 20260915141808.png]]

토스에서는 `BottomSheet, Dialog, Toast`와 같이 화면 위에 뜨는 오버레이를 띄워야 하는 상황이 많다
이렇게 오버레이를 띄우는 동작을 추상화하여 `useOverlay`라고 하는 `Hook`을 사용한다


```tsx
const overlay = useOverlay();

<button 
	onClick={() => { 
		overlay.open(({ isOpen, close }) => {
		 return ( 
		 <BottomSheet open={isOpen} onClose={close}> 
		 나는 바텀시트야 
		 </BottomSheet> 
		 );
	  })
  }} 
> 
		  바텀시트 열기 
	  </button>
```


만약 `useOverlay` 가 없었더라면 아래와 같이 제어 흐름이 드러나는 코드를 작성했어야 할 것이다

```tsx
const [isSheetOpen, setIsSheetOpen] = useState(false);
 
 <button 
	 onClick={() => setIsSheetOpen(true)}> 
	 바텀시트 열기 
 </button> 
 <BottomSheet 
	 open={isSheetOpen} 
	 onClose={() => setIsSheetOpen(false)}> 
	 나는 바텀시트야 
 </BottomSheet>
```


- #### ImpressionArea
- ---
토스 앱에서는 어떤 영역이 보여졌는지/숨겨졌는지에 따라서 동작하는 로직이 많다
예를 들어서, 사용자가 특정한 요소를 보면 폭죽을 터뜨리거나 토스트를 보여주는 식이다
토스에서는 `ImpressionArea` 라고 하는 컴포넌트로 이를 추상화하고 있다

```tsx
	<ImpressionArea onImpressionStart={() => { /* 보여졌을 때 실행 */ }}> 
		<div>내가 보여졌으면 onImpressionStart가 실행돼</div> 
	</ImpressionArea>
```


`ImpressionArea` 가 없었더라면, 복잡한 `IntersectionObserver` API 를 사용하거나, 복잡한 Scroll 이벤트 핸들러 로직을 사용해야 했을 것이다

- #### LoggingClick
- ---
토스에서는 데이터 주도 의사결정을 위해서 화면에 진입하는 사용자가 몇 명인지, 그 중 몇 명이 버튼을 누르는지를 기록하는 경우가 있다
이런 누르는 동작에 대한 기록을 추상화하여 `LoggingClick` 컴포넌트를 사용하고 있다

```tsx
	<LoggingClick params={{ price }}> 
		<button onClick={buy}>사기</button> 
	</LoggingClick>
```

`LoggingClick` 이 없었다면 아래와 같이 `log` 함수를 실행하는 것이 그대로 드러났어야 할 것이다

```tsx
	<button 
		onClick={() => { 
			log({ title: '사기', price }); 
			buy(); 
		 }} > 
		사기 
	</button>
```
