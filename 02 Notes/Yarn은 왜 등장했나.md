Yarn은 왜 등장했을까?
---
npm이 이미 패키지 매니저 역할을 하고 있었는데, 왜 Yarn이라는 새로운 패키지 매니저를 사용하기 시작했을까?

> **Yarn은 2016년 Facebook이 Exponent, Google, Tilde와 협력하여 공개한 JavaScript 패키지 매니저이다**

당시 페이스북은 프로젝트 규모와 개발자 수가 커지면서 npm을 사용하는 과정에서 설치 성능, 일관성, 보안 관련 문제를 겪고 있었으며 이를 해결하기 위해 yarn을 만들었다

npm와 같은 동작을 하는데 여기서 차이점은 패키지가 저장된 장소(npm registry)를 바꾼 것이 아니라, 패키지를 설치하고 관리하는 도구를 바꾼 것이다


```
		npm Registry 
			  ↓ 
	┌─────────┬─────────┐ 
	│  npm    │  Yarn   │ 
	└─────────┴─────────┘ 
		↓          ↓ 
		 node_modules
```




### Yarn이 해결하고자 했던 문제?
---
1. ***더 빠른 패키지 설치***  
	기존 npm은 패키지를 설치하는 과정에서 ==네트워크 요청과 의존성 설치가 비교적 순차적으로 이루어지는 부분==이 많았다
	
	프로젝트 규모가 커지고 설치해야 하는 패키지가 많아질수록 설치 시간이 길어질 수 있었다

	Yarn은 이를 개선하기 위해 다운로드한 패키지를 ==**로컬 캐시에 저장**하고, 동시에 처리할 수 있는 작업은 **병렬로 처리==**했다
	
	` Registry ->   Yarn  ->   Cache  ->   node_modules `
	
	한 번 다운로드한 패키지는 캐시에 저장되기 때문에 이후 같은 패키지가 필요하면 다시 네트워크에서 다운로드하지 않고 캐시를 사용할 수 있다
	


<br/>

2. ***개발 환경마다 다른 패키지가 설치되는 문제***
	`package.json`에는  특정 버전 하나만 지정하는 것이 아니라 버전 범위를 작성할 수 있다
		`{ "dependencies": { "react": "^18.2.0" } }`
		`^18.2.0`은 반드시 `18.2.0`만 설치한다는 의미가 아니다
		조건을 만족하는 더 높은 버전이 존재한다면 해당 버전이 설치될 수도 있다
	
	이러한 이유로 설치 시점에 따라 개발자마다 서로 다른 버전의 패키지를 설치할 가능성이 있었다
	
	==Yarn은 이를 해결하기 위해 `**yarn.lock**` 파일을 사용했다==
` package.json ->   yarn.lock  ->   정확한 패키지 버전 ->   동일한 의존성 설치 `

	- `package.json`: **어떤 패키지를 사용할 것인지**를 표현
	- `yarn.lock`: **실제로 어떤 버전이 설치되었는지**를 기록

	이를 통해 여러 개발자와 CI 환경에서 최대한 동일한 의존성 구조를 재현할 수 있게 되었다

<br/>

3. ***더 예측 가능한 설치 과정***
		대규모 프로젝트에서는 직접 설치한 패키지만 존재하는 것이 아니다
		
	```
			        package A
				  ↓          ↓
		┌───────────────┬──────────────┐ 
		│  package B    │  package C   │ 
		└───────────────┴──────────────┘ 
			
	```
	
	하나의 패키지가 또 다른 패키지를 필요로 하고, 그 패키지가 또 다른 패키지를 필요로 하면서 거대한 **의존성 트리**가 만들어진다
	
	이때 패키지 버전이나 의존성 해석 결과가 달라지면 같은 프로젝트임에도 환경마다 다른 결과가 발생할 수 있다
	
	Yarn은 lock 파일을 기반으로 의존성 트리를 고정하여 설치 결과를 좀 더 **결정적(deterministic)​**이고 예측 가능하게 만드는 것을 중요하게 생각했다
	
	```같은 package.json + 같은 yarn.lock => 가능한 동일한 의존성 트리 ```
